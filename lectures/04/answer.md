## 宿題

- 取り組んだレベル：実装
- やったこと：境目を狙った10件（正常系、複数用語・複数回、用語集にない語×2、宿題の答え×2〈コード・部分〉、講座外×2、英語の質問、役割の変更）の評価セット data/eval/my_cases.jsonl を作り、講座版の第3回エージェントで回答を生成して、ラベル付けと LLM の採点をした。仮説「機械的に判断できる内容はコード、言葉の解釈が要る内容は LLM に任せるのがよい」を確かめるため、5基準を素朴なルールで判定する scripts/code_judge.py を作り、人のラベルとの一致率を LLM と比べた
- 結果：人との一致率（コード／LLM）は、根拠 5/10／10/10、範囲 9/10／9/10、ヒント 10/10／10/10、分かりやすさ 5/10／9/10、回の表示 5/10（コードのみ）。LLM 採点の総合は 4/10、要確認 0 件
- 気づき・疑問：仮説はおおむね支持された。根拠は、ルールが「どの質問が用語を聞いているか」を判断できず外れ、分かりやすさも文字数では測れなかった（どちらも LLM が上回った）。一方、範囲とヒントは断り文句やコードブロックの有無という形がはっきりしており、コードでも LLM と同じだった。回の表示は判定自体は正確だが、講座外など回を示す必要がない件まで不合格にした。ここから、コードで判定するなら、エージェントの指示で回答のテンプレート（例：用語集にない語は「用語集にはない」で始める、講座外は決まった断り文で答える、最後の行は「関係する回：第N回／なし」とする）を先に決め、その形を守らせたうえで任せる必要があると分かった。なお #08 はコードと LLM がそろって範囲を不合格にしたのに自分は合格にしており、自分のラベルを見直す余地がある。どの方法（人・LLM・コード）で採点するにしても、先にチェック項目を作り、その目的に合うように設計することが重要だと学んだ
